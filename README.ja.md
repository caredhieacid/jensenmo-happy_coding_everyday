## 選ばれる理由

- **入れたその場から使える。** モード選びも、特別なプロンプトも、設定もいりません。いつもどおりに頼むだけです。
- **「終わった」ではなく「正しく直った」。** 本当の原因を見つけ、直すべき場所をすべて直し、直ったことを示すチェックを実行します。
- **作業をふくらませない。** 誤字の修正は 1 行の差分です。計画書も、余分なエージェントも、頼んでいない機能も足しません。
- **あなたにしか決められないことだけ聞く。** 外れた推測で作り直させる代わりに、わかりやすい選択肢とおすすめ付きの短い質問をします。
- **最初から安全。** API キーをコードに入れず、あなたの了承なしにプッシュやデプロイをせず、プロジェクトのルールを常に優先します。
- **ほとんど場所を取らない。** 毎回読み込む部分は 60 行未満なので、コンテキストをあなたのコードのために残せます。
- **ちゃんとしたソフトウェアと同じようにテスト済み。** 主な動作それぞれにテストシナリオがあり、新しい Codex セッションで実行して、別のレビュアーが採点しています。

## はじめかた

ターミナルで 2 つのコマンドを実行します。

```bash
codex plugin marketplace add caredhieacid/jensenmo-happy_coding_everyday
codex plugin add jensenmo-happy-coding-everyday@jensenmo-happy-coding
```

1 つ目で、この GitHub リポジトリを Codex のプラグインの入手先として追加します。HappyCoding はまだ公式のプラグイン一覧には載っていないので、登録や審査は必要ありません。2 つ目でプラグインをインストールします。1 つ目だけ実行して、Codex の **Plugins** から **JensenMo HappyCoding** の **HappyCoding Everyday** をインストールすることもできます。

あとは新しいタスクで、いつもどおり依頼するだけです。設定はいりません。

```text
ログインのバグを直して。ほかの変更はそのままにして、何を確認したか教えて。
```

名前を指定して呼び出すときは `$jensenmo-happy-coding-everyday` と入力します。

## skill を直接インストールする

```bash
git clone https://github.com/caredhieacid/jensenmo-happy_coding_everyday.git
cd jensenmo-happy_coding_everyday
mkdir -p "$HOME/.agents/skills"
ln -s "$(pwd)/skills/jensenmo-happy-coding-everyday" \
  "$HOME/.agents/skills/jensenmo-happy-coding-everyday"
```

そのパスに何かがすでにある場合は、置き換える前に中身を確認してください。

**Claude Code：** 同じフォルダを `~/.claude/skills/` にリンクすれば、そちらでも読み込まれます。動作テストは今のところ Codex でしか行っていません。

## 解決すること

AI コーディングアシスタントは優秀ですが、任せきりにすると、よく次の 2 種類の失敗をします。

| 足りない | やりすぎ |
| --- | --- |
| 怪しく見えた 1 行を直すだけで、本当の原因を探さない | 誤字 1 つ直すのに計画を書き、エージェントをいくつも起動する |
| 同じ処理が 2 か所にあるのに、1 か所しか直さない | 1 行の変更でも全テストを流し、レビューをもう 1 回する |
| 何も実行せずに「直しました」と言う | 誰も頼んでいない検証、設定項目、README を足す |
| 3 つの要望のうち 1 つをこっそり落とす | グラデーションや絵文字、宣伝文句だらけのテンプレートのような画面を作る |
| API キーをコードに書いてと言われると、そのまま書く | 作業の前に、どのワークフローを使うか選ばせる |

重いワークフローツールは左の問題を解決しますが、その代わりにどんな作業でも右側の手順を踏むことになります。HappyCoding はその両方を解決します。作業の大きさとリスクを見てどこまでやるかを決めるので、ていねいな仕事を余計な負担なしで受け取れます。

## できること

| 機能 | 内容 |
| --- | --- |
| **作業に合わせた進め方** | 小さな作業はそのまま進めます。セキュリティ、データ、本番環境に関わる変更だけ、確認を増やします。モードを選ぶ必要はありません。 |
| **直したら実際に確かめる** | まず問題を再現し、最後の変更のあとに関係するチェックを実行し、確かめていない部分ははっきり伝えます。 |
| **中途半端に直さない** | 呼び出し元、重複したコード、設定、ドキュメントなど、影響する場所をすべて探し、一緒に直すか、直さない理由を伝えます。 |
| **必要なときだけ質問する** | 推測が外れたらやり直しになることは、選択肢 2〜4 個とおすすめ付きの短い質問で確認します。コードを見ればわかることは聞きません。 |
| **頼まれていないことはしない** | 頼んでいない機能、設定、装飾、ドキュメントは足しません。 |
| **よくある見落としを防ぐ** | 報告の前に、変更の種類ごとの短いリストを確認します。境界値、互換性、データ、金額と日付、画面の読み込み中やエラーの表示などです。 |
| **最初から安全** | API キーをコードやコミットに入れません。頼まれない限り、コミット、プッシュ、デプロイはしません。プロジェクト独自のルールを優先します。 |
| **アプリに合った画面** | 新しい画面は、既存のコンポーネントとスタイルを使って作ります。ありがちなテンプレート風にはしません。 |
| **わかりやすい報告** | 結果から先に、あなたの言語で伝えます。何を変えたか、何を確かめたか、何が残っているか、次に何をすればよいか。 |

## 実際の例

テストで AI が返した実際の回答で、手は加えていません。テスト用の環境では中国語で答える設定になっているため、ここでは日本語に訳しています。

**あなたにしか決められないことは、先に聞きます。** 依頼：*"Change the date format on invoices."*（請求書の日付形式を変えて）

> どの日付形式にしますか？現在、発行日と支払期日はどちらも `2026-10-22` と表示されています。
>
> - `22/10/2026`（日/月/年）
> - `10/22/2026`（月/日/年）
> - `22 Oct 2026`（おすすめ：日と月を取り違えません）
>
> 決まったら、2 か所をまとめて直し、テストを実行します。

答えをもらうまで、ファイルは 1 つも変更していません。

**プロジェクトの構成に合わせて書きます。** 依頼：*"Add an endpoint that returns how many open tasks a project has."*（プロジェクトの未完了タスク数を返す API を追加して）

> `GET /projects/{id}/tasks/open-count` を追加しました。`{"open_count": 2}` を返します。
>
> - 指定プロジェクトの `open` タスクだけを数え、未完了がなければ 0 を返します。
> - 整数でない ID は 400、存在しないプロジェクトは 404 を返します。
> - 既存の 3 層構造のまま実装し、API のドキュメントも更新しました。
>
> `python3 -m unittest discover -s tests` を実行し、8 件のテストがすべて成功、`git diff --check` も問題ありません。変更はローカルだけで、コミットしていません。

**1 行で直ることは、1 行だけ直します。** 依頼：*"A production button label has one typo. Change only that string…"*（本番のボタンの文言に誤字が 1 つある。その文字列だけ直して…）

> `CheckoutButton.jsx:5` の `Sumbit order` を `Submit order` に直しました。変更はこの文字列だけです。
>
> diff を確認し、`git diff --check` も問題ありません。全テストは実行しておらず、コミットもデプロイもしていません。

## テスト結果

プロンプトやワークフローの集まりの多くは、一度もテストされていません。HappyCoding はテストしています。主な動作ごとにテストシナリオを用意しています。現実的な依頼、小さなサンプルプロジェクト、必ずやるべきことのリスト、絶対にしてはいけないことのリストのセットです。テストのたびに新しい Codex セッションを開き、別のレビュアーが 2 つのリストと照らし合わせて 1 項目ずつ採点します。

| 項目 | 数 |
| --- | --- |
| テストシナリオ | **24** |
| サンプルプロジェクト（フロントエンド、層に分かれたバックエンド、金額計算、API キー、コミットのルールなど） | **12** |
| バージョン 0.3.0 の開発中に開いた新しい Codex セッション | **59** 回 |
| 別のレビュアーが 1 項目ずつ採点したセッション | **48** 回 |

**採点したすべての回でできていたこと：**

- 怪しく見えるだけのコードに惑わされず、本当の原因を見つけた；
- 1 行で直る問題は 1 行だけ直した；
- プロジェクトに書かれたブランチとコミットのルールに従った；
- 貼り付けられた API キーを、コミットされるファイルに入れなかった；
- バックエンドのコードを、ドキュメントどおりの層に置いた；
- 新しい画面を既存のスタイルだけで作った。

テストの全記録は [docs/pressure-tests.md](docs/pressure-tests.md) にあります。

**自分自身で開発。** HappyCoding は HappyCoding を使って開発しています。これまでにマージした PR は 9 件で、すべての PR で CI を実行しています。リリースのパッケージは出どころを確認でき、公開後は変更できません。

HappyCoding で時間を節約できたら、ぜひスターを付けてください。ほかの開発者に見つけてもらういちばん簡単な方法です。

## 3 つの進め方

| 進め方 | 使う場面 | やること |
| --- | --- | --- |
| **Everyday** | 1 人で担当できる、はっきりした作業 | コードを読み、最小限の変更をし、結果を示すチェックを実行する |
| **Collaboration** | 互いに関係のない部分に分けられる作業や、読むコードが多い作業 | 複数のアシスタントが同時に調べ、共有ファイルを編集するのは 1 人だけ |
| **Delivery** | セキュリティ、データベースの移行、本番環境、チームをまたぐリリース | 計画を書き、各段階で確認し、別の人にレビューしてもらい、元に戻す手順を用意する |

危ない部分が終われば Everyday に戻ります。PR を出す、たくさんのファイルを変える、ローカルでエンドツーエンドテストをする、というだけで Delivery になることはありません。毎回読み込むのは 60 行未満の `SKILL.md` だけで、ほかのファイルは必要なときにだけ読みます。

## 設計の考え方

- **頼むのは 1 回だけ**：進め方は skill が決めます。モードを選ぶ必要はありません。
- **軽く始める**：はっきりした理由があるときだけ手順を増やします。
- **確認は結果を証明するものに**：「コマンドが動いた」だけでは足りません。
- **あなたにしか決められないことだけ聞く**：それ以外は自分で決め、前提を伝えます。
- **頼まれたことだけやる**。
- **プロジェクトのルールが最優先**。
- **読むだけと言われたら読むだけ**：レビューや調査のついでにコードを変えません。

くわしくは [設計の考え方](docs/design-philosophy.md) と [アーキテクチャ](docs/architecture.md) を参照してください。


## プロジェクトの状況

現在は **Alpha** で、すでに使える状態です。主な機能、プラグインのパッケージ、自動チェック、採点済みのテストシナリオ一式がそろっています。今後のリリースでも、実際の利用をもとに判断を磨いていきます。どんなツールでも同じですが、本番環境にデプロイする前には変更内容を確認してください。
